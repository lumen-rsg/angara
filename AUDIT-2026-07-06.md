## 🟠 High-Severity (0 deferred)

### H8. Field Overwrite Leak — `this.field = x` Silently Leaks Old Field Value — ✅ RESOLVED
**File:** `StmtAnalysis.cpp:133-156` (cross-function seeding), `ExprAnalysis.cpp:238-285` (field overwrite + UAF)  

All four sub-items now implemented:
1. **Within-method field overwrite leak (E501):** AssignExpr handler tracks field state in StateMap; overwrite while Live → E501.
2. **`drop this.field` syntax:** Parser extended, DropStmt holds target Expr; Chaperone resolves field types via TypeChecker; LLVM emits `__ang_record_get` + cascade + `__ang_record_set(nil)`.
3. **Field-level UAF (E502):** GetExpr handler checks field state keys; Dropped/Moved fields trigger E502/E507 on access.
4. **Cross-function field tracking:** Non-constructor methods seed tracked `this` fields as Live at entry, so the first overwrite in a regular method triggers E501 unless the field was explicitly dropped. Constructors are exempt (fields start uninitialized).

Tests:
- `38_e501_field_overwrite_leak.an` — within-method overwrite → E501
- `39_e503_field_double_drop.an` — double drop → E503
- `40_e502_field_use_after_drop.an` — read after drop → E502
- `41_e501_nonthis_field_overwrite.an` — non-this overwrite → E501
- `42_e502_nonthis_field_uaf.an` — non-this UAF → E502
- `43_e501_crossfn_field_overwrite.an` — cross-function overwrite → E501
- `22_field_drop_and_reassign.an`, `23_nonthis_field_drop_reassign.an`, `24_crossfn_field_drop_reassign.an` — drop + reassign → OK
- `05_move_into_field.an` — updated for cross-function tracking

### H9. FFI Default-Borrow — Unannotated Foreign Functions Cause Silent Double-Free — ✅ RESOLVED
**File:** `Type.h:120-145`, `FuncStmt.cpp:102-136`, `ExprAnalysis.cpp:340-380`  

Every foreign/module call without explicit `@consumes`/`@escape` annotations defaults to **Borrow**. A C function like `sqlite3_close(db)` that takes ownership and frees its argument, called without `@consumes(0)`, causes a **silent double-free** — the Angara caller still thinks the argument is Live and may drop it.

**Resolution (2026-07-07):**  
1. `@consumes`/`@escape` annotations stored on `FunctionType` — persist across module boundaries (`attach`).  
2. Chaperone call-site fallback: when no summary is found by name, builds a temporary summary from the callee's `FunctionType` annotations.  
3. Pre-loop annotation injection (Chaperone.cpp:384-404) already handled same-file foreign funcs; the `FunctionType` fallback extends this to attached module funcs.

Tests:
- `44_e503_foreign_consumes_double_drop.an` — `@consumes(0)` foreign func → E503 double-drop
- `25_foreign_consumes.an` — `@consumes(0)` annotated func → ownership correctly transferred

### H10. Indirect Calls Default to Borrow — Function Pointer Double-Free Undetected — ✅ RESOLVED
**File:** `Chaperone.h:86-91`, `StmtAnalysis.cpp:451-460`, `ExprAnalysis.cpp:206-216,382-396`  

Calls through function pointers could not be name-resolved, so the summary defaulted to Borrow. If the pointed-to function actually dropped, the caller could double-free.

**Resolution (2026-07-07):**  
1. Added `function_aliases` map to Chaperone `Context` — tracks variable name → function name when a variable is assigned a direct function reference.  
2. `VarDeclStmt` handler records aliases on `let f = someFunc;` when `someFunc` has a summary.  
3. `AssignExpr` handler updates aliases on `f = someFunc;` reassignments.  
4. `CallExpr` handler resolves indirect calls through aliases before falling back to Borrow — uses the aliased function's summary.

Limitations: Unresolvable indirect calls (function pointers received as parameters, computed function pointers) still default to Borrow.

Tests:
- `45_e503_indirect_call_double_drop.an` — indirect call through consuming function pointer → E503 double-drop
- `26_indirect_consume.an` — indirect call through consuming function pointer → correctly consumed, no error
- `18_indirect_call.an` — updated documentation

## 🟡 Medium-Severity (4 deferred)

### Chaperone

#### M12. `ref<T>` borrows through `data` struct fields untracked — dangling ref — ✅ RESOLVED
**Location:** `ExprAnalysis.cpp`, `StmtAnalysis.cpp`  
**Resolution (2026-07-07):**

When a `ref<T>` is taken to a field of a tracked struct (e.g., `let r as ref<Buf> = c.buf`), the Chaperone now records the borrow relationship — the ref borrows the parent object. A later drop of the parent while the ref still aliases its field memory triggers E509 (dangling borrow). Four code paths were fixed:

1. **AssignExpr with GetExpr target** (`ExprAnalysis.cpp:286-296`): When the target field resolves to `ref<T>`, assigning a tracked Live variable is now treated as a borrow rather than a move — the source stays Live and the field-keyed borrow is recorded.
2. **GetExpr read** (`ExprAnalysis.cpp:667-685`): When reading a field that resolves to `ref<T>`, the Chaperone now checks `ctx.borrows` for the field key and verifies the referent is still Live. If the referent was dropped/moved, E509 fires.
3. **VarDeclStmt struct literal** (`StmtAnalysis.cpp:432-467`): When a non-owned data struct is initialized with a RecordExpr, any `ref<T>` fields assigned from tracked Live variables are recorded in `ctx.borrows`.
4. **VarDeclStmt GetExpr initializer** (`StmtAnalysis.cpp:500-538`): When a new `ref<T>` variable is initialized from a struct field access, the borrow is propagated — either from an existing `ref<T>` field borrow, or directly from the parent tracked object.

Tests:
- `53_e509_dangling_ref_field.an` — ref to owned struct field, parent dropped → E509
- `27_ref_field_safe.an` — ref to owned struct field used before parent drop → OK

#### M13. Generic type parameters may not resolve before monomorphization
**Location:** `ExprAnalysis.cpp`  

The Chaperone runs before monomorphization, so it cannot analyze ownership for generic type parameters whose concrete types are unknown. Some generic functions may pass the Chaperone but produce unsound monomorphized code.

**Status:** DEFERRED — Requires either monomorphization-before-Chaperone or bounded parametric analysis.

### Testing & CI

#### M25. No type-checker, Chaperone, or codegen unit tests in C++ suite
**Location:** `tests/cpp/`  

The C++ test suite only covers the lexer and parser fuzzer. There are no unit tests for the type checker, Chaperone memory analysis, or LLVM codegen — making regression prevention dependent entirely on integration-level language tests.

**Status:** DEFERRED — Significant test writing effort required.

#### M27. Fuzz only covers lexer/parser, not type checker or codegen
**Location:** `tests/cpp/test_fuzz.cpp`  

The fuzz harness feeds random bytes to the lexer and parser, but doesn't exercise the type checker, Chaperone, or codegen — where more subtle bugs are likely to hide.

**Status:** DEFERRED — Test infrastructure enhancement needed.

## 🔵 Low-Severity (8 deferred)

### Compiler

- **L8.** All async locals boxed as full `AngaraObject` (128-bit), even `i64` counters (`TopLevel.cpp:386-414`). DEFERRED: architectural change to allow unboxed async locals for small types.

- **L11.** GC terminology persists throughout the codebase despite v5 garbage collector removal (cosmetic). ACKNOWLEDGED: full rename touches ~50 call sites for no functional benefit.

### Chaperone

- **L21.** Closure capture always Escaped (E505) even for synchronous-only use — false positive. **PARTIALLY RESOLVED:** IIFE (immediately-invoked function expressions) and closures passed as arguments to functions that Borrow the parameter are now detected and no longer trigger E505. Full escape analysis for closure variables stored in locals still deferred.

- **L22.** Container cycles (e.g., `list<B>` where `B → A`) not detected as E504. DEFERRED: architectural — requires cycle detection in the Chaperone's escape analysis.

- **L23.** Return of tracked value as `ref<T>` incorrectly treated as ownership escape. DEFERRED: architectural — requires distinguishing returning-a-ref from escaping-ownership.

- **L24.** Loop-post-dominance false positive — conservative Live-after-loop. DEFERRED: architectural — the Chaperone conservatively marks values as Live after loops even when the loop always drops them.

### Standard Library & Ecosystem

- **L30.** Missing `.an` interface files for most modules (only 3 originally). **PARTIALLY RESOLVED:** Interface files written for 6 key modules (io, fs, math, net, time, json) in `docs/interfaces/`. Full type-checked integration requires compiler support for native-module interface forwarding (`.an` → `.so` linkage). Remaining ~27 modules still need interface files.

- **L35.** No Windows build support at all. DEFERRED: platform support — the codebase is Linux + macOS only, with no Windows build system, platform abstractions, or CI coverage.

## 📝 Methodology

This audit examined the entire Angara codebase (~175 source files, ~15,000 lines) across six independent deep-dive analyses:

1. **Compiler frontend** (lexer, parser): All expression/statement/declaration parsers, token handling, error recovery
2. **Type system & type checker**: Type.h (1000+ lines), SymbolTable, TypeChecker, all expression/statement visitors
3. **Chaperone memory safety**: Full Chaperone.cpp, all expression/statement analysis, all 53 test files, CHAPERONE.md design doc
4. **LLVM codegen backend**: Full LLVMBackend.cpp, all expression/statement codegen, runtime support, async lowering, debug info
5. **Standard library**: All 52 `.c` files across 12 module categories, `Angara.h` FFI header, module Makefile infrastructure
6. **Tests & build system**: All test suites, CI workflow, full Makefile (483 lines), `.clang-tidy`, `.clang-format`

Each analysis was performed independently and cross-referenced for consistency. Findings were classified using a standard severity taxonomy:
- **Critical:** Security vulnerability or data-loss risk exploitable in normal use
- **High:** Correctness bug that produces wrong results, silent data corruption, or unsound safety guarantees
- **Medium:** Bug or limitation that can be triggered in specific scenarios
- **Low:** Code quality issue, cosmetic concern, or enhancement opportunity
