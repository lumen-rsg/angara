# 🔍 Angara Language — Comprehensive Audit Report

**Date:** 2026-07-06  
**Audit scope:** Full-stack — compiler frontend, type system, Chaperone memory safety, LLVM backend, standard library, tests, build system, CI/CD  
**Version under audit:** v5.1.0 (commits through 4527406)  
**Findings:** 3 Critical · 19 High · 29 Medium · 36 Low  

---

## Executive Summary

Angara is a **remarkably ambitious and well-executed** compiler project for a statically-typed systems language. The architecture — recursive-descent parser → type checker → Chaperone memory verifier → LLVM codegen — is clean and coherent. The code is in C++23 with consistent RAII, smart pointers, and proper use of modern patterns.

However, the language is **not yet production-ready**. The audit identified **3 critical security vulnerabilities** in the standard library C code, **19 high-severity correctness issues** spanning the compiler, memory model, and build system, and significant gaps in test coverage and CI enforcement. The Chaperone memory model — the language's flagship safety innovation — has real soundness holes that allow silent memory leaks and double-frees in common patterns.

**Verdict:** A solid v5.1.0. The language is mature enough for serious personal projects and exploration. Production deployment, especially in security-sensitive contexts, should wait until the critical and high findings below are addressed.

## 1. 🔴 Critical Findings (Must Fix Before Production Use)

### C1. Path Traversal in Archive Extraction — Zip Slip Vulnerability ✅ RESOLVED
**File:** `modules/fs/archive.c:175, 265`  
Archive entries are extracted by naive string concatenation: `snprintf(fullpath, ..., "%s/%s", destdir, pathname)`. An archive containing `../../etc/passwd` as a filename writes outside the destination directory. No path sanitization or realpath validation is performed. This is a textbook Zip Slip vulnerability (CWE-22).

**Impact:** Any Angara program using `fs.archive.extract()` on untrusted archives can be exploited for arbitrary file write.  
**Fix:** Added `path_is_safe()` helper that rejects absolute paths and paths containing `..` components. Both `zip_extract` and `tar_extract` now skip entries that fail this check.

### C2. Shell Injection via `popen()` in Process Module ✅ RESOLVED
**File:** `modules/system/process.c:18`  
`process.exec()` calls `popen(ang_api->as_cstr(args[0]), "r")`, which invokes `/bin/sh -c` with user-provided input. Any program passing untrusted data to this function gets full shell command injection.

**Impact:** Remote code execution if an Angara program uses `process.exec()` with any externally-influenced input.  
**Fix:** Replaced `popen()` with `fork()` + `execvp()`. Added a `tokenize_command()` helper that splits the command string into argv while respecting single/double quotes, completely bypassing the shell.

### C3. `realloc` Failure → Memory Leak + Null Dereference ✅ RESOLVED
**File:** `modules/io/eventloop.c:122, 567`  
```c
r->entries = (CbEntry*)realloc(r->entries, r->cap * sizeof(CbEntry));
memset(r->entries + r->count, 0, ...);  // SIGSEGV if realloc returned NULL
```
If `realloc` returns NULL, the original pointer is overwritten (leak) and `memset(NULL + offset, ...)` writes to near-null — immediate crash or undefined behavior.

**Fix:** Use a temporary variable; check for NULL before reassigning. Both `cb_registry_add()` and `pending_add()` now use a temp pointer and bail out on allocation failure.

## 2. 🟠 High-Severity Findings

### Compiler Frontend (Lexer & Parser)

#### H1. `std::stoi`/`stoll`/`stoul` Overflow → Unhandled Exceptions → Compiler Crash ✅ RESOLVED
**Files:** `Lexer.cpp:203,223,294`; `Parser.cpp:93`; `dispatcher.cpp:21,40`; `interpStringExpression.cpp:51,76`  

Integer literals exceeding the range of `int`, `long`, or `unsigned long` throw `std::out_of_range` or set `errno` (for `strtol`). These exceptions are never caught, causing the compiler to crash on malformed but syntactically valid input.

**Impact:** Denial of service — a single malformed source file crashes the compiler.  
**Fix:** All `std::stoi`/`std::stoll`/`std::stoul` calls in the parser now catch `std::out_of_range` and `std::invalid_argument`, throwing `ParseError` with a descriptive message. `strtol` calls in the lexer check `errno` for `ERANGE`. Interpolated string parsing catches overflow silently (truncation is safe for escape sequences).

#### H2. No Recursion Depth Limit → Stack Overflow ✅ RESOLVED
**Files:** `unaryExpression.cpp:13`, `ternaryExpression.cpp:11`, `assignmentExpression.cpp:14`  

Right-recursive parsing of `!!!!!!!!!!!...x`, chained ternaries, and chained assignments recurses without bound. ~10,000 nested operators overflow the C++ call stack and crash the compiler.

**Fix:** Added `m_recursionDepth` counter to the `Parser` class. Each recursive call in `unary()`, `ternary()`, and `assignment()` increments the counter; if it exceeds 256, a `ParseError` is thrown with a descriptive message instead of crashing the compiler.

#### H3. Discarded `error()` Return Value — Invalid Assignments Produce Incorrect AST ✅ RESOLVED
**File:** `assignmentExpression.cpp:43`  
```cpp
error(op, "Invalid assignment target.");
// falls through — NO throw, returns expr as-is
```
The `ParseError` returned by `error()` is discarded. The parser continues with a malformed AST. The error IS reported but the AST is wrong, causing confusing cascading errors downstream.

**Fix:** Added `throw` before `error()`: `throw error(op, "...");`

#### H4. `catch (...)` Swallows Fatal Exceptions (Including OOM) ✅ RESOLVED
**File:** `interpStringExpression.cpp:176`  
Intended to catch `ParseError` from sub-parsers, but the overly broad `catch (...)` also swallows `std::bad_alloc`, signals, and other fatal conditions.

**Fix:** Catch `const ParseError&` specifically.

### Type System & Type Checker

#### H5. `extract_type_args` Doesn't Recurse Into Wrapped Types — Generic Inference Broken for Optionals, Refs, Futures, Tuples ✅ RESOLVED
**File:** `TypeChecker.cpp:637-663`  

Generic type inference only recurses into `LIST`, `GENERIC_INSTANCE`, and `TYPE_PARAM`. It misses `OPTIONAL`, `REF`, `FUTURE`, `TUPLE`, `FUNCTION`, `RECORD`, `POINTER`, `FIXED_ARRAY`, `RAW_ARRAY`, `VECTOR`. This means `func first<T>(x: T?) -> T` **cannot infer `T` from a `string?` argument**. This is a significant limitation for generic programming.

**Fix:** Extended `extract_type_args` with cases for all ten wrapper type kinds, each extracting the inner type(s) and recursing. Size/depth guards added for TUPLE, FUNCTION, FIXED_ARRAY, POINTER, and VECTOR to ensure structural compatibility before recursing.

#### H6. Trait Default Method Bodies Are Never Type-Checked ✅ RESOLVED
**File:** `TraitStmt.cpp:4-5`  

`visit(TraitStmt)` has an **empty body**. Default method implementations stored in `trait_type->default_bodies` are never visited by the type checker. Any type error in a trait's default methods silently passes.

**Fix:** `visit(TraitStmt)` now iterates over all default bodies, sets up a scope with parameter declarations matching the trait's method signatures, and visits each body's statements. Type errors in trait default implementations are now caught during compilation.

#### H7. Documented Token Default-Construction → Uninitialized `type` Field ✅ RESOLVED
**File:** `Token.h:79`, `Token.cpp:150-152`  

`Token()` default-constructs with uninitialized `type` (only `line` and `column` have `{}` initializers). If any code path reads `type` from a default-constructed token, it's undefined behavior. Currently masked by callers that avoid reading it, but fragile.

**Fix:** Added `TokenType type = TokenType::EOF_TOKEN;` default initializer.

### Chaperone Memory Safety

#### H8. Field Overwrite Leak — `this.field = x` Silently Leaks Old Field Value — DEFERRED
**File:** `ExprAnalysis.cpp:247` (documented as S6-PARTIAL)  

The Chaperone does not track per-field ownership. When a method reassigns a tracked-type field, the old allocation is **silently leaked** with no diagnostic:
```angara
this.inner = new Buf(1);
this.inner = new Buf(2);  // first Buf LEAKED — no error
drop this;                 // only second Buf is dropped
```

**Status:** DEFERRED — Requires per-field state tracking in the Chaperone, a significant architectural change.

#### H9. FFI Default-Borrow — Unannotated Foreign Functions Cause Silent Double-Free — DEFERRED
**File:** `ExprAnalysis.cpp:347`  

Every foreign/module call without explicit `@consumes`/`@escape` annotations defaults to **Borrow**. A C function like `sqlite3_close(db)` that takes ownership and frees its argument, called without `@consumes(0)`, causes a **silent double-free** — the Angara caller still thinks the argument is Live and may drop it.

**Impact:** Every FFI binding is a potential soundness hole unless meticulously annotated.  
**Status:** DEFERRED — Requires `@consumes`/`@escape` annotation system for foreign functions.

#### H10. Indirect Calls Default to Borrow — Function Pointer Double-Free Undetected — DEFERRED
**File:** `tests/chaperone/positive/18_indirect_call.an` (explicitly documented)  

Calls through function pointers cannot be name-resolved, so the summary defaults to Borrow. If the pointed-to function actually drops, the caller may double-free. The test itself acknowledges this is undetected.

**Status:** DEFERRED — Inherently hard to solve statically; requires runtime checks or restricting function pointers.

### LLVM Codegen

#### H11. Async State Machine May Incorrectly Resume Across Branches — DEFERRED
**File:** `TopLevel.cpp:675-677`  

The async lowering assigns linear state numbers to await points regardless of control flow. If `await` appears inside an `if`/`else`, the two branches get different state numbers, but the dispatch switch may jump to a state from the wrong branch on resumption, executing code in the wrong control-flow context.

**Impact:** Potentially incorrect async program behavior.  
**Status:** DEFERRED — Requires control-flow-aware state encoding in async lowering.

#### H12. No Division-by-Zero Checking — Generated Code Has Undefined Behavior — DEFERRED
**Files:** `ExprCodegen.cpp:531, 586` (+ shift operations)  

`SDiv`, `UDiv`, and `FDiv` are emitted without zero checks. Division by zero in LLVM IR produces `undef` (undefined behavior). Similarly, shift amounts >= bitwidth produce `undef`.

**Impact:** Correct Angara programs that divide by zero have undefined behavior at runtime instead of a controlled exception.  
**Fix:** Emit runtime checks before divisions and shifts, branching to a panic/exception on zero divisor or excessive shift.

### Standard Library (C Code)

#### H13. Thread-Unsafe Static Initialization In Crypto Module ✅ RESOLVED
**Files:** `hash.c:37-38`, `tls.c:24-30`  

CRC32 lookup table and OpenSSL are initialized lazily on first use without any mutex. Two threads calling `hash.crc32()` simultaneously may read a partially-initialized table.

**Fix:** Replaced ad-hoc `init_flag` pattern with `pthread_once_t` / `pthread_once()` in both `hash.c` (CRC32 table) and `tls.c` (OpenSSL init).

#### H14. `fread` Return Value Not Checked → Heap Information Disclosure ✅ RESOLVED
**File:** `modules/fs/fs.c:36`  

```c
fread(buffer, sizeof(char), file_size, file);
buffer[file_size] = '\0';  // assumes full read
```
Partial reads leave uninitialized heap data in the buffer, which gets wrapped in an Angara string and exposed to the program — an information disclosure vulnerability.

**Fix:** Capture `fread` return value and use `bytes_read` for null-termination and string length, ensuring only actually-read data is exposed.

#### H15. Integer Overflow in Decompression Buffer Sizing ✅ RESOLVED
**Files:** `modules/fs/archive.c:39, 91`  

```c
size_t dest_len = data_len * 4;  // overflow if data_len > SIZE_MAX/4
```
Maliciously crafted compressed data can trigger integer overflow, allocating a tiny buffer that receives a much larger decompressed output — heap buffer overflow.

**Fix:** Added overflow guard before multiplication: `if (data_len > SIZE_MAX / 4)` with an error throw. Applied to both `gzip_decompress` and `zlib_decompress`.

### Build System & CI

#### H16. CI Only Triggers on `stable` Branch — No PR/Feature-Branch Testing ✅ RESOLVED
**File:** `.github/workflows/main.yml:6-11`  

CI only runs on pushes/PRs to `stable`. All development on feature branches gets zero CI coverage until merged, defeating the purpose of CI for catching regressions.

**Fix:** Changed CI trigger to all branches (`push:` and `pull_request:` with no branch filter). Release job and artifact upload restricted to `refs/heads/stable` to prevent nightly releases from feature branches.

#### H17. No Sanitizers in CI (ASAN, UBSAN, TSAN) ✅ RESOLVED
**File:** `.github/workflows/main.yml:74`  

The plain `make all` build uses no sanitizer flags. For a compiler that manages memory (Chaperone) and links against C standard library code, sanitizers are essential.

**Fix:** Added `sanitizers` CI job that builds with `-fsanitize=address,undefined` and runs C++ unit tests, Chaperone tests, and language tests under ASAN+UBSAN. Also resolves M26 (Chaperone tests not in CI).

#### H18. No `DESTDIR` Support → Packaging Impossible ✅ RESOLVED
**File:** `Makefile:398-406`  

Install targets copy directly to `/usr/local/bin` and `/opt/angara/modules` with no `DESTDIR` prefix. This makes downstream packaging (deb, rpm, homebrew) impossible.

**Fix:** Prefixed all install paths with `$(DESTDIR)`, e.g. `$(DESTDIR)$(INSTALL_BIN_DIR)`. DESTDIR defaults to empty, so existing usage is unaffected.

#### H19. `.d` Dependency Files Don't Work on First Build ✅ RESOLVED
**File:** `Makefile:482`  

`-include build/obj/**/*.d` uses a glob expanded at make parse time, before any `.d` files exist on a clean build. Header changes require **two** `make` invocations to trigger recompilation.

**Fix:** Replaced glob with `$(shell find build/obj -name '*.d' 2>/dev/null)` which reliably discovers .d files at parse time on every invocation.

## 5. 🏗️ Architectural Observations

### What's Excellent
1. **Pipeline design** — Lexer → Parser → Type Checker → Chaperone → LLVM Codegen is clean and well-separated
2. **Chaperone interprocedural analysis** — Fixed-point convergence algorithm is elegant and proven to terminate in ≤8 passes
3. **FFI design** — `AngaraObject` tagged union, API vtable, `native_instance_new` with finalizers is idiomatic and efficient
4. **Error recovery** — Panic-mode synchronization in the parser is well-implemented
5. **Precedence climbing** — Correct and handles right-associativity (assignment, ternary)
6. **UTF-8 escape processing** — `\u`, `\U`, `\u{...}` handling is thorough, including surrogate rejection
7. **async/await lowering** — Heap-allocated frame struct with waker-based suspension is a solid v1 design
8. **Module ecosystem breadth** — 36 native modules covering a respectable surface area for a young language
9. **Test organization** — Chaperone tests with `// expect: Exxx` headers set a high bar for negative testing
10. **Tree-sitter grammar** — Complete and well-maintained across 755 lines

### What Needs Architectural Work
1. **Chaperone per-field tracking** — The biggest soundness gap. Reassigning struct fields silently leaks allocations. This is the #1 item to fix for the Chaperone to deliver on its "no leaks" promise.
2. **FFI safety annotations** — The default-Borrow for all foreign calls is too permissive. A mandatory annotation system or `@nosafe` marker on foreign declarations would close this significant soundness hole.
3. **`throw_error` resource leak** — Systemic across the standard library. Either the runtime needs a `defer` mechanism for C resources, or all C resources must be wrapped in native instances with finalizers. The current state means that error paths in every module silently leak.
4. **Concurrency model** — The Chaperone has zero concurrency awareness. Before multi-threaded Angara programs become a thing, the ownership model must be extended to cover thread boundaries, `Send`/`Sync`-like traits, and data-race protection.
5. **Async state machine correctness** — The branch-oblivious state numbering is a correctness risk that should be addressed before async is considered stable.
6. **Test output validation** — Tests only check "compiles and doesn't crash." Adding expected-output validation (file-based golden tests, or inline `// expect: "output"` annotations) would dramatically improve confidence.

## 6. 📊 Language Maturity Assessment

| Dimension | Rating | Notes |
|-----------|--------|-------|
| **Parser robustness** | ⭐⭐⭐⭐ | Good panic-mode recovery, solid precedence. Crashes on overflow (#H1) and deep nesting (#H2). |
| **Type system soundness** | ⭐⭐⭐ | Core type checking is solid but generic inference is incomplete (#H5) and trait defaults unchecked (#H6). |
| **Memory safety guarantees** | ⭐⭐⭐ | Chaperone prevents common errors but has real holes: field-overwrite leaks (#H8), FFI bypass (#H9), indirect calls (#H10). |
| **Codegen correctness** | ⭐⭐⭐ | LLVM IR generation is solid for common cases. Async has potential branch bug (#H11). No div-zero checks (#H12). |
| **Standard library** | ⭐⭐⭐ | Good breadth but 3 critical vulns (#C1–C3) and systemic resource leak (#M19). |
| **Test coverage** | ⭐⭐ | Good chaperone tests but huge gaps: no output validation, missing negative tests, no codegen unit tests. |
| **CI/CD** | ⭐⭐ | Runs but bare minimum: no sanitizers, only on `stable`, no chaperone tests in CI. |
| **Build system** | ⭐⭐ | Functional but fragile: no DESTDIR, hardcoded paths, silent pkg-config failures, .d file issues. |

## 8. 📝 Methodology

This audit examined the entire Angara codebase (~175 source files, ~15,000 lines) across six independent deep-dive analyses:

1. **Compiler frontend** (lexer, parser): All expression/statement/declaration parsers, token handling, error recovery
2. **Type system & type checker**: Type.h (1000+ lines), SymbolTable, TypeChecker, all expression/statement visitors
3. **Chaperone memory safety**: Full Chaperone.cpp, all expression/statement analysis, all 53 test files, CHAPERONE.md design doc
4. **LLVM codegen backend**: Full LLVMBackend.cpp, all expression/statement codegen, runtime support, async lowering, debug info
5. **Standard library**: All 52 `.c` files across 12 module categories, `Angara.h` FFI header, module Makefile infrastructure
6. **Tests & build system**: All test suites, CI workflow, full Makefile (483 lines), `.clang-tidy`, `.clang-format`

Each analysis was performed independently and cross-referenced for consistency. Findings were classified using a standard severity taxonomy:
- **Critical:** Security vulnerability or data-loss risk exploitable in normal use
- **High:** Correctness bug that produces wrong results, silent data corruption, or unsound safety guarantees
- **Medium:** Bug or limitation that can be triggered in specific scenarios
- **Low:** Code quality issue, cosmetic concern, or enhancement opportunity
