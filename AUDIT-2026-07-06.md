## 🔵 Low-Severity (6 deferred)

### Compiler

- **L8.** All async locals boxed as full `AngaraObject` (128-bit), even `i64` counters (`TopLevel.cpp:386-414`). **RESOLVED:** Async frame slots now use unboxed LLVM types for primitive locals (bool→i1, int→i64, float→double). `collectAsyncLocals` looks up each variable's type via the TypeChecker and records the appropriate `LocalKind`; frame struct fields use `llvmTypeForLocalKind`; `loadVar`/`storeVar` async paths box/unbox based on `namedKinds`. Params remain boxed (ABI passes them boxed). Build and full test suite (90/90) pass.

- **L11.** GC terminology persists throughout the codebase despite v5 garbage collector removal (cosmetic). **RESOLVED:** All ~80 call sites across 15 files renamed from `gc`/`Gc` prefix to `rt`/`Rt` (runtime). LLVM IR functions (`__ang_gc_*` → `__ang_rt_*`), C++ members (`m_fn_gc_*` → `m_fn_rt_*`, `m_gc_*` → `m_rt_*`), method names (`emitGc*` → `emitRt*`, `getGc*` → `getRt*`), struct types (`GcRootFrame` → `RtRootFrame`, `GcThreadState` → `RtThreadState`), and benchmark files updated. Build and full test suite (90/90) pass.

### Chaperone

- **L21.** Closure capture always Escaped (E505) even for synchronous-only use — false positive. **PARTIALLY RESOLVED:** IIFE (immediately-invoked function expressions) and closures passed as arguments to functions that Borrow the parameter are now detected and no longer trigger E505. Full escape analysis for closure variables stored in locals still deferred.

- **L22.** Container cycles (e.g., `list<B>` where `B → A`) not detected as E504. DEFERRED: architectural — requires cycle detection in the Chaperone's escape analysis.

- **L23.** Return of tracked value as `ref<T>` incorrectly treated as ownership escape. DEFERRED: architectural — requires distinguishing returning-a-ref from escaping-ownership.

- **L24.** Loop-post-dominance false positive — conservative Live-after-loop. DEFERRED: architectural — the Chaperone conservatively marks values as Live after loops even when the loop always drops them.

### Standard Library & Ecosystem

- **L30.** Missing `.an` interface files for most modules (only 3 originally). **PARTIALLY RESOLVED:** Interface files written for 6 key modules (io, fs, math, net, time, json) in `docs/interfaces/`. Full type-checked integration requires compiler support for native-module interface forwarding (`.an` → `.so` linkage). Remaining ~27 modules still need interface files.

- **L35.** No Windows build support at all. DEFERRED: platform support — the codebase is Linux + macOS only, with no Windows build system, platform abstractions, or CI coverage.

## 📝 Methodology

This audit examined the entire Angara codebase (~175 source files, ~15,000 lines) across six independent deep-dive analyses:

1. **Compiler frontend** (lexer, parser): All expression/statement/declaration parsers, token handling, error recovery
2. **Type system & type checker**: Type.h (1000+ lines), SymbolTable, TypeChecker, all expression/statement visitors
3. **Chaperone memory safety**: Full Chaperone.cpp, all expression/statement analysis, all 53 test files, CHAPERONE.md design doc
4. **LLVM codegen backend**: Full LLVMBackend.cpp, all expression/statement codegen, runtime support, async lowering, debug info
5. **Standard library**: All 52 `.c` files across 12 module categories, `Angara.h` FFI header, module Makefile infrastructure
6. **Tests & build system**: All test suites, CI workflow, full Makefile (483 lines), `.clang-tidy`, `.clang-format`

Each analysis was performed independently and cross-referenced for consistency. Findings were classified using a standard severity taxonomy:
- **Critical:** Security vulnerability or data-loss risk exploitable in normal use
- **High:** Correctness bug that produces wrong results, silent data corruption, or unsound safety guarantees
- **Medium:** Bug or limitation that can be triggered in specific scenarios
- **Low:** Code quality issue, cosmetic concern, or enhancement opportunity
