## Executive Summary

This third audit examined four subsystems not deeply covered in the prior audits: the **Chaperone** compile-time memory safety pass, the **compiler frontend** (type checker, parser, lexer), the **module system** (native module isolation, package manager, build system), and the **LLVM codegen backend**. A total of **55 findings** were identified:

| Severity | Count | Key themes |
|----------|-------|-----------|
| **Critical** | 10 | Unsound Chaperone join, overly-optimistic FFI defaults, unconditional Send/Sync marking, command injection in build system, SHA256 never verified, native module symbol leakage, broken async closure captures, variadic C ABI wrong, narrowed type lost to codegen, ERROR type-guard dead code |
| **High** | 12 | Missing ForInStmt tracking, non-transitive closure escape, GENERIC_INSTANCE interface adoption broken, parser stack-overflow DoS, TRAIT_OBJECT missing from type substitution, isTruthy accepts all types, exception frame struct fragmentation, cgDrop nil guard insufficient, IO read_all exponential memory allocation, lockfile parser fragile, registry JSON parser vulnerable, no redirect protocol restriction |
| **Medium** | 18 | Various type-checker gaps, cast safety, symbol table collisions, thread safety issues, path traversal, bounds checks missing, hardcoded allocation sizes, version pinning bypass, trait objects not tracked correctly |
| **Low** | 15 | Debug info, ABI documentation, hash fragility, portability gaps, code quality issues |

The language has **strong foundations** but four critical soundness holes in the Chaperone's join logic, combined with module-isolation and codegen-correctness issues, mean it is **not yet ready for production deployment where memory safety guarantees are relied upon**. The fixes needed are well-understood and moderate in scope — none requires architectural redesign.

# 🔴 Critical Findings

---

### ✅ C1. Chaperone join function is unsound: `Live` dominates dead states at branch merges — **RESOLVED** (7aad15e)

**Severity:** Critical  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/Chaperone.cpp:36-43`

```cpp
Chaperone::State Chaperone::join(State a, State b) {
    if (a == b) return a;
    if (a == State::Live || b == State::Live) return State::Live;
    return State::Dropped;
}
```

The join rule "if either branch is Live, the result is Live" means a variable that escapes on one branch of an `if` but is still Live on the other is treated as Live after the merge. Consider:

```angara
let x = alloc();
if (cond) { f(x); }  // @escape: x becomes Escaped
// join(Escaped, Live) = Live — Chaperone thinks x is still valid
use(x);  // No error — silent use-after-escape on the @escape path
```

The asymmetry warnings (W510) are emitted but as non-fatal warnings. The merged state remains Live, and subsequent uses on paths where the value was Escaped/Moved go undetected. This is the root cause of systematic unsoundness across all branch merges.

**Trigger:** Call an `@escape`-annotated function on a tracked variable inside an `if`-without-`else`, then use the variable after the `if`.

**Fix:** When a variable is Live on one path and dead (Escaped/Moved/Dropped) on the other, the merged state must conservatively be the dead state, OR the asymmetry diagnostic must be upgraded to a hard error that blocks compilation. The conservative fix is:

```cpp
// If either side is "gone," the merged state must be gone.
if (a == State::Escaped || b == State::Escaped) return State::Escaped;
if (a == State::Moved || b == State::Moved) return State::Moved;
if (a == State::Dropped || b == State::Dropped) return State::Dropped;
if (a == State::Live || b == State::Live) return State::Live;
return State::Uninit;
```

### ✅ C2. Unknown function calls default to Borrow — unsound for FFI — **RESOLVED** (2ee3254)

**Severity:** Critical  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/expr/ExprAnalysis.cpp:709`

```cpp
// else: Unknown function — default is BORROW (no state change).
```

When a CallExpr's callee has no Chaperone summary (not found by name, not a closure, no `@consumes`/`@escape` annotations), all Live tracked arguments are kept Live. The Chaperone assumes the unknown callee borrows. If the callee is a foreign C function that actually takes ownership (frees the argument), the Chaperone silently misses the use-after-free.

**Trigger:** Call an unannotated foreign function that internally frees a tracked argument, then use that argument again.

**Fix:** The default for truly unknown functions should be `Escaped` (conservative). Alternatively, require all foreign/module functions with tracked parameters to carry `@consumes` or `@escape` and emit an error when an unannotated call passes a tracked Live argument.

### ✅ C7. Command injection via unsanitized `cflags`/`ldflags` in build system — **RESOLVED** (1fba88b)

**Severity:** Critical  
**Component:** Build System  
**File:** `angc/backend/build_system/BuildSystem.cpp:486-488,517`

```cpp
if (!mod.cflags.empty()) cmd << " " << mod.cflags;
if (!mod.ldflags.empty()) link_cmd << " " << mod.ldflags;
```

The `cflags` and `ldflags` fields from the project `.abs` configuration are inserted directly into shell command strings without escaping. An attacker who controls or influences the `.abs` file can inject arbitrary shell commands. While `shell_escape` is used for source file paths, these flags are raw user input.

**Trigger:** A crafted `.abs` file with `cflags = "-O2; rm -rf /"`.

**Fix:** Pass flags as a list parsed from a JSON array, individually escape each flag, or validate that flags contain only safe characters. Better yet, use `execvp`-style argument passing instead of `std::system`.

### ✅ C8. Command injection via package name in tar extraction path — **RESOLVED** (9e75ed7)

**Severity:** Critical  
**Component:** Package Manager  
**File:** `angc/backend/package/PackageManager.cpp:61`

```cpp
std::string cmd = "cd " + pkg_dir.string() + " && tar xzf package.tar.gz 2>/dev/null";
int result = std::system(cmd.c_str());
```

The `pkg_dir` path is constructed from user-controlled package name and version. If a registry returns a maliciously crafted package name (e.g., `"pkg; rm -rf /"`), shell metacharacters are injected. Additionally, `tar xzf` without `--no-same-owner` or `--no-overwrite-dir` allows a malicious tarball to overwrite system files or set setuid bits.

**Trigger:** A compromised registry serving a package with a malicious name or tarball.

**Fix:** Use `shell_escape` on the path, add `--no-same-owner --no-overwrite-dir`, validate tarball paths don't contain `..`, and replace `std::system` with a proper library.

### ✅ C9. SHA256 integrity check is never performed on downloaded packages — **RESOLVED** (cd7f194)

**Severity:** Critical  
**Component:** Package Manager  
**File:** `angc/backend/package/PackageManager.cpp:40`

```cpp
if (fs::exists(pkg_dir)) {
    // Already installed — could verify sha256 here
    return true;
}
```

The lockfile stores a `sha256` field for each package, recorded after download. However, the SHA256 hash is **never verified** against downloaded content. The comment on line 40 explicitly acknowledges this gap. A compromised registry or MITM attacker can replace a package tarball with malicious code, and the package manager will install it without detection.

**Trigger:** Any package download where the registry is compromised or a MITM attack substitutes the tarball.

**Fix:** After downloading the tarball and before extraction, compute the SHA256 and compare it against the known-good hash from the lockfile (or registry, cross-checked). Fail the install on mismatch.

### ✅ C10. Closure captures silently broken inside async functions — **RESOLVED** (6abd631)

**Severity:** Critical  
**Component:** LLVM Codegen  
**File:** `angc/backend/llvm/expr/ExprCodegen.cpp:2896-3015`

In async functions, local variables are stored in the heap-allocated frame struct, not in stack allocas. The closure capture loop in `cgLambda` iterates over `namedVals` to find captured variables. In `codegenAsyncResumeFunc`, `namedVals` is cleared (line 627) and never repopulated for async frame locals (only `m_async_local_slots` is populated). Consequently, any closure defined inside an async function captures **zero** variables from the enclosing scope. All closed-over references silently load nil/zero values — no compiler error, no runtime error, just wrong results.

**Trigger:** Define a lambda inside an `async` function that references any local variable from the enclosing async scope.

**Fix:** In `cgLambda`, when `m_in_async_function` is true, iterate over `m_async_local_slots` and load each variable from the async frame into the heap-allocated capture array, using the `loadVar`/`storeVar` abstraction.

### ✅ H1. Missing ForInStmt loop variable tracking — **RESOLVED** (c82dcd6)

**Severity:** High  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/stmt/StmtAnalysis.cpp:1111-1118`

The `for-in` loop variable is never added to the Chaperone state map. If the element is of a tracked type, the body cannot track its state — drops, moves, and escapes of the loop variable are invisible to the Chaperone.

**Fix:** Add the loop variable to the state map (as Live if tracked) before analyzing the body.

---

### H2. ReturnStmt does not transitively escape captures of nested closures

**Severity:** High  
**Component:** Chaperone  
**File:** `angc/backend/chaperone/stmt/StmtAnalysis.cpp:839-864`

When a closure is returned, direct captures are marked Escaped. But if a captured variable is itself a closure, its own captures are NOT transitively escaped. Those inner captures remain Live and may be spuriously flagged as leaks.

**Fix:** Perform transitive closure of the capture graph when escaping a closure at return/throw/call sites.

### H3. `adoptsInterface` returns false for `GENERIC_INSTANCE` subject types

**Severity:** High  
**Component:** Type Checker  
**File:** `angc/analyzer/type_checker/stmt/ClassStmt.cpp:311-336`

`adoptsInterface` casts the subject only to `InstanceType` or `TraitObjectType`. When the subject is a `GenericInstanceType` like `Box<MyDrawable>`, the function returns `false` even if the underlying type adopts the interface. This blocks legitimate upcasts from generic instances to trait types.

**Fix:** Unwrap `GENERIC_INSTANCE` → base type before checking adoption.

### H5. `GenericInstanceType::substitute` and `substituteTypeArgs` missing `TRAIT_OBJECT` case

**Severity:** High

### H8. Exception frame struct type created independently in four places

**Severity:** High  
**Component:** LLVM Codegen  
**Files:** `StmtCodegen.cpp:479-481`, `ControlFlow.cpp:267-270,294-297,319-322`, `LLVMBackend.cpp:964-966`

The exception frame struct `{ [N x i8], ptr }` is created with `StructType::create` in four different locations using two different names. If anyone changes `jmp_buf_size` in one place but not another, the GEP offsets diverge, causing stack corruption on `longjmp`.

**Fix:** Define the exception frame struct once in `RuntimeBuilder::generateTypes()` and reference it everywhere.

### H10. `cgDrop` nil guard does not protect against non-OBJ types

**Severity:** High  
**Component:** LLVM Codegen  
**File:** `angc/backend/llvm/stmt/StmtCodegen.cpp:666-668`

The nil guard in `cgDrop` checks only `TAG_NIL` before extracting the payload as a heap pointer. If a non-heap-allocated value (e.g., a bare integer) reaches a `drop` statement, the numeric payload is treated as a pointer, calling `finalize` and `free` on a fabricated address.

**Fix:** Also verify the tag is `TAG_OBJ` before treating the payload as a pointer.

---

### H11. IO `read_all` has exponential memory allocation due to C++ ternary bug on `Value*`

**Severity:** High  
**Component:** LLVM Runtime  
**File:** `angc/backend/llvm/rt/IO.cpp:362-364`

```cpp
bl.CreateCondBr(is_done, done_bb, is_full ? grow_bb : loop_bb);
```

`is_full` is a `llvm::Value*`, not a `bool`. In C++, any non-null pointer is truthy, so the ternary always selects `grow_bb`. Every partial `fread` that doesn't reach EOF doubles the buffer — for a typical stdin read of several KB, this causes exponential growth.

**Fix:** Split into two sequential conditional branches instead of a ternary.

---

### H12. Lockfile JSON parser uses fragile raw string search

**Severity:** High  
**Component:** Package Manager  
**File:** `angc/backend/package/Lockfile.cpp:184-200`

After an initial JSON parse, the lockfile loader uses raw `content.find("\"packages\"")` and `content.find('{', colon)` to locate and re-parse the packages object. If any version string, SHA256 hash, or field value contains the literal text `"packages"`, the wrong occurrence is matched. Escaped `\"packages\"` inside strings is also incorrectly matched.

**Fix:** Use a single-pass recursive-descent JSON parser for the entire lockfile.

### M1. Chaperone convergence check ignores `closure_summaries`

**File:** `angc/backend/chaperone/Chaperone.cpp:548-575`  
Only `ctx.summaries` is compared for fixed-point convergence. `ctx.closure_summaries` (populated during lambda body analysis) is not included. If closure summaries change while function summaries stabilize, the loop terminates prematurely with stale closure data.

**Fix:** Include `ctx.closure_summaries` in the convergence comparison.

### M2. AwaitExpr Send-check uses name-based lookup vulnerable to shadowing

**File:** `angc/backend/chaperone/expr/ExprAnalysis.cpp:1053-1092`  
The O(n×m) scan of `var_types` matches by string name. If two variables in different scopes share the same name (shadowing), the wrong declaration may be matched, producing incorrect E516 diagnostics.

**Fix:** Store VarDeclStmt pointers alongside state entries rather than matching by name.

if (dynamic_cast<const NestedPattern*>(pat.get())) continue;

Variables bound inside nested patterns are invisible to the Chaperone — leaks, use-after-free, and closure captures involving those variables go undetected.

### M5. Destructure assignment does not propagate `ref<T>` borrow relationships

**Fix:** After tuple destructure, iterate elements and record borrows for `ref<T>` elements.

## 🏁 Readiness Assessment

**Is Angara ready for serious projects?**

**Not yet — but close.** The language has a clear vision, excellent documentation, and most of the hard engineering is done. However, three categories of issues must be resolved first:

1. **Chaperone soundness (blocking):** The join-function flaw (C1) and the overly-optimistic FFI default (C2) mean the Chaperone can silently miss use-after-escape and use-after-free in common patterns (branching + function calls). These are not theoretical — they are triggerable in normal code. The fixes are well-understood and modest in scope (~20 lines of code each).

2. **Codegen correctness (blocking for async users):** Async closure captures being silently broken (C10) means any non-trivial async code with closures produces wrong results with no diagnostic. The variadic C ABI bug (H9) affects FFI correctness.

3. **Supply-chain security (blocking for package ecosystem):** Command injection in the build system (C7) and package manager (C8), combined with no SHA256 verification (C9) and no module isolation (C6), mean the package ecosystem is not trustable. These need to be fixed before anyone should `angara install` a third-party package.

### What's already solid:
- The Chaperone design (CHAPERONE.md) is well-thought-out and documented
- The type checker covers most cases correctly
- The test suites are comprehensive
- The standard library is broad
- The LLVM integration is professional
- Cross-platform support (Linux, macOS, Windows, ARM64) works

### Recommended priority order for resolution:

| Priority | Finding | Effort | Impact |
|----------|---------|--------|--------|
| **P0** | C1 — Chaperone join unsoundness | ~1 hour | Closes the biggest soundness hole |

## 📝 Methodology

This audit examined the Angara codebase (~175 source files, ~20,000 lines) across four independent deep dives:

1. **Chaperone memory safety** (`Chaperone.cpp`, `ExprAnalysis.cpp`, `StmtAnalysis.cpp`, `Chaperone.h`): State machine, join logic, interprocedural analysis, ref-borrow checking, concurrency safety, exception unwinding, cycle detection.

2. **Compiler frontend & type checker** (`TypeChecker.cpp`, `Type.h`, `SymbolTable.cpp`, `CallExpr.cpp`, `BinaryExpr.cpp`, `AssignExpr.cpp`, `ReturnStmt.cpp`, `VarDeclStmt.cpp`, `FuncStmt.cpp`, `ClassStmt.cpp`, `Parser.cpp`, `Lexer.cpp`, and 25+ individual expression/statement type-checking files): Type system soundness, inference, trait resolution, error handling, parser robustness, lexical analysis.

3. **Module system** (`CompilerDriver.cpp`, `PackageManager.cpp`, `RegistryClient.cpp`, `Lockfile.cpp`, `Version.cpp`, `BuildSystem.cpp`, `ConfigParser.cpp`, `DependencyGraph.h`, `ModuleAPI.cpp`, `AngaraABI.h`, `ModuleLister.cpp`, and representative native modules): Isolation, name resolution, package supply-chain security, build system safety, ABI stability.

4. **LLVM codegen backend** (`LLVMBackend.cpp`, `ExprCodegen.cpp`, `StmtCodegen.cpp`, `TopLevel.cpp`, `RuntimeBuilder.cpp`, `Memory.cpp`, `Strings.cpp`, `ControlFlow.cpp`, `Conversions.cpp`, `IO.cpp`): IR correctness, async lowering, exception handling, debug info, runtime operations, ABI conformance.

Each analysis was performed independently with spot-checks across modules for consistency. All critical findings were verified against source code.
